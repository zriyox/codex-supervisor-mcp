Сайт [agent-supervisor.zriyo.com](https://agent-supervisor.zriyo.com) · для моделей [llms.txt](https://agent-supervisor.zriyo.com/llms.txt) · [справочник](docs/reference.en.md) (на английском)

Если натравить несколько агентов на один репозиторий, они затирают работу друг друга, никто не может сказать, кто что поменял, а контекст основного потока забивается выводом воркеров.

agent-supervisor-mcp — это MCP-сервер. Основной поток (Claude Code, Codex или любой MCP-клиент) запускает через него несколько воркеров Codex CLI одновременно: у каждого воркера свой Git worktree, состояние хранится в SQLite, а следить за ними можно на веб-доске. Раздача задач и учёт живут на диске, а не в контексте модели.

![Демо: основной поток Claude Code раздаёт задачи трём воркерам Codex в отдельные worktree, ждёт и сводит результат](https://raw.githubusercontent.com/zriyox/agent-supervisor-mcp/main/assets/demo.gif)

*30 секунд, записано вживую: три воркера параллельно в своих worktree, затем основной поток собирает три diff и делает один коммит.*

> **Раньше пакет назывался codex-supervisor-mcp.** Его переименовали, потому что воркер теперь не только Codex. Машину со старым пакетом переводит его последний релиз: ставится этот пакет, регистрация MCP и skill становятся `agent-supervisor`, а каталог состояния остаётся на месте. Префикс утилит командной строки меняется с `codex-supervisor-` на `agent-supervisor-`.
>
> **Переход с 0.x на 1.x**: 39 инструментов превратились в 14, с новыми именами и аргументами, старые имена не сохранены. Сначала доведите до конца запущенных воркеров, а после обновления откройте сессию заново, чтобы подгрузился новый skill. Таблица инструментов в [справочнике](docs/reference.en.md), что изменилось — в [релизе 1.0.0](https://github.com/zriyox/agent-supervisor-mcp/releases/tag/v1.0.0).

## Что он решает

| Проблема | Что он делает |
|---|---|
| Воркеры наступают друг другу на файлы | У каждого воркера свой worktree; пересечение `owned_paths` проверяется до запуска |
| Вывод воркеров заливает основной поток | События пишутся в JSONL; основной поток читает сжатую сводку (все воркеры меньше чем в 7000 байт) |
| После перезапуска или в новой сессии воркеры теряются | Одна строка SQLite на задачу, с её `thread_id`; `resume_worker` возвращается в ту же сессию Codex |
| Упавший запуск не отличить от умершего процесса | Машина состояний разделяет `failed` и `lost`, а у сбоя есть источник и код |
| Воркер говорит, что всё готово, а это не так | Задача уходит с командами `acceptance`; супервизор сам запускает их после выхода воркера и не даёт влить результат, если они упали |
| Изменения так и остаются в локальной ветке | `land_worker` вливает их в интеграционную ветку; `verify_push` подтверждает, что коммит есть на remote |
| Worktree копятся | Влитые и пустые удаляются при опросе. Невлитая работа хранится 7 дней, и перед удалением worktree её незакоммиченные правки коммитятся в её ветку. Ветки и доказательства остаются |

По умолчанию воркер — это процесс `codex exec`, а `model` передаётся как есть. Основной поток остаётся на Claude, воркеры работают на DeepSeek или другом провайдере, и счета не смешиваются.

Воркером может быть и Claude Code: передайте `runner: "claude"` в `create_worker`. У него нет песочницы ОС, поэтому он работает только в git worktree или в режиме только для чтения, и у него нет побочного чата (`ask_worker`); запуск, приёмка, продолжение, вливание и очистка такие же. Как подключить другой CLI, описано в [docs/runner.md](docs/runner.md).

## Пять минут до первой партии

Нужны Node.js 22.13.0 или новее и `codex` CLI в `PATH`. Работает на macOS, Linux и Windows.

```bash
npm install -g agent-supervisor-mcp
```

Скрипт установки кладёт skill во все найденные Claude Code и Codex и регистрирует MCP-сервер. После этого перезапустите их. Если ничего не зарегистрировалось (например, с `--ignore-scripts`), запустите `agent-supervisor-setup` или добавьте вручную:

```bash
claude mcp add -s user agent-supervisor -- npx -y agent-supervisor-mcp
codex mcp add agent-supervisor -- npx -y agent-supervisor-mcp
```

GUI-клиентам вроде Claude Desktop, Cursor и Windsurf конфигурацию MCP нужно поправить руками; фрагмент есть в [справочнике](docs/reference.en.md#environment-variables). Только skill, без сервера: `npx skills add zriyox/agent-supervisor-mcp`.

Дальше скажите в Claude Code обычными словами:

> Допиши юнит-тесты для этих трёх модулей. Используй agent-supervisor, три воркера параллельно, назови сессию «юнит-тесты».

Skill проведёт основной поток по таким шагам:

```
preflight_worker     сначала пробный запуск в том же окружении
create_worker ×3     каждому session, owned_paths, goal
wait_workers         не больше 60 секунд за вызов; вызывать снова, пока не закончится
get_worker ×3        отчёт каждого воркера, с командами, которые он запускал, и их кодами выхода
get_worker_diff ×3   что он на самом деле поменял
land_worker ×3       проверено; закоммитить за него и влить
```

Воркеры никогда не коммитят сами. Их изменения лежат в `worker/<taskId>`, пока основной поток не прочитает diff.

Чтобы смотреть, как они работают, откройте доску:

```bash
agent-supervisor-web     # или: npx -p agent-supervisor-mcp agent-supervisor-web
```

Откройте `http://127.0.0.1:7877`. Там видны воркеры каждой сессии: статус, команда, которая выполняется прямо сейчас, изменения и события. Воркеру можно задать вопрос сбоку: ответ приходит из копии его треда только для чтения, так что текущая работа не прерывается. Доска только показывает. Запускать и отменять воркеров с неё нельзя.

## Как я им пользуюсь

Основным потоком может быть всё, что говорит на MCP; это просто мой способ. Я держу две сессии Claude Code: одну для документов, другую для раздачи задач. Одна сессия, которая и пишет проект, и следит за воркерами, забивает контекст за два часа.

| Кто | Где | Что делает |
|---|---|---|
| Я | | Решаю, что строить, принимаю решения, читаю отчёты |
| Сессия планирования | Репозиторий требований и документации | Обсуждает требование, пишет проект, пишет по одному брифу на блок работы |
| Сессия «главного мозга» | Worktree репозитория с кодом | Читает бриф, раздаёт задачи воркерам, проверяет diff, отчитывается мне. Сама бизнес-код не пишет |
| Воркеры Codex | Свои worktree | Один воркер на функциональный пакет, который можно проверить отдельно. Без коммитов и push |

Между двумя сессиями передаётся один блок текста: его вставляют в сессию главного мозга и отдают через `/goal`:

```text
[Роль]          Ты главный мозг: раздаёшь задачи воркерам, проверяешь результат, обновляешь доки, отчитываешься мне.
                Бизнес-код ты не пишешь. Сначала загрузи skill agent-supervisor.
[Контекст]      Зачем нужен этот блок, что осталось от предыдущего
[Сначала прочти] Какие разделы каких документов и какой главнее, если они расходятся
[Сделать]       Следуй таблице из раздела N брифа. Ничего сверх таблицы
[Раздача]       Сначала find_works, чтобы ничего не запустить дважды; один session.id на партию;
                параллельно только при непересекающихся наборах файлов; команда проверки идёт и в acceptance;
                словам воркера не верить, верить diff, который ты прочитал
[Красные линии] Что не менять, не пушить и не читать
[Отчёт]         Сначала таблицы, потом остановись и жди меня
```

## Инструменты

По умолчанию их четырнадцать. Аргументы и пограничные случаи — в [справочнике](docs/reference.en.md#tools).

| Этап | Инструмент | Что делает |
|---|---|---|
| До запуска | `preflight_worker` | Запускает короткую пробу в окружении будущего воркера или сначала по-настоящему прогоняет команды приёмки |
| Запуск | `create_worker` | Запускает одного воркера. С `followup_of` продолжает работу другого воркера |
| | `resume_worker` | Продолжает ту же сессию, при желании сначала перебазировав её на новую голову |
| | `cancel_worker` | Останавливает воркера |
| Наблюдение | `poll_workers` | Без курсора — вся таблица; с курсором — только то, что изменилось, плюс восстановление умершего первого запуска и удаление worktree, которые можно удалить безопасно |
| | `wait_workers` | Ждёт результата, не больше 60 секунд за вызов |
| Сбор результата | `get_worker` | Читает одного воркера: сводку, отчёт, статус, события, цель — какие части попросите |
| | `get_worker_diff` | Реальные изменения, постранично по файлам и hunk |
| | `ask_worker` | Задаёт воркеру вопрос сбоку. Только чтение; его тред не трогается |
| Сдача | `land_worker` | Коммитит за воркера и делает cherry-pick в интеграционную ветку; отказывает, если приёмка упала |
| | `verify_push` | Подтверждает, что влитый коммит есть на remote. Только проверяет, сам за вас не пушит |
| | `cleanup` | Показывает, почему worktree ещё на месте, или удаляет его сразу. Обычно очистка идёт сама |
| Партии | `find_works` | Снова находит партию или ищет по истории подстрокой |
| | `describe_session` | Записывает название партии, цель, приёмку по умолчанию и статус согласования |

Ещё три регистрируются только с `AGENT_SUPERVISOR_TOOLS=all`: `facts` (реестр проверенных фактов), `review` (независимый проверяющий только для чтения) и `get_artifact` (сохранённые доказательства). Обычной партии они не нужны, а без них в каждой сессии экономится контекст.

## Чем это отличается от subagent в Claude Code

Subagent тоже может открыть свой worktree, так что разница не в изоляции файлов. Разница в модели и процессе.

| | Subagent Claude Code | Воркер agent-supervisor |
|---|---|---|
| Какие модели | Только Claude | Любые, для которых у Codex CLI есть провайдер |
| Кто выполняет работу | Сам Claude Code | Отдельный процесс `codex exec` |
| Два воркера пишут один файл | Пути не объявляются | Пересечение `owned_paths` проверяется до запуска, и запуск отклоняется |
| Основной поток умер | Результат не забрать | Воркеры и приёмка доходят до конца; новое окно снова находит их через `find_works` |
| Кто может управлять | Только Claude Code | Любой MCP-клиент |
| Видно ли процесс | Только итоговый вывод | Сырой JSONL и веб-доска |

## Настройка и состояние

Всё лежит в `~/.agent-supervisor` (машина, обновлённая с codex-supervisor-mcp, у которой уже есть `~/.codex-supervisor`, продолжает пользоваться им): `data/supervisor.sqlite` — это реестр, `data/runs/<taskId>.jsonl` — сырой вывод Codex, а в `worktrees/<taskId>/` лежит рабочая копия каждого воркера.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SUPERVISOR_HOME` | `~/.agent-supervisor` | Корень состояния. MCP-сервер и доска должны смотреть в один и тот же |
| `CODEX_BIN` | `codex` | Путь к Codex CLI. У GUI-клиентов его часто нет в `PATH` |
| `SUPERVISOR_WEB_PORT` | `7877` | Порт доски |
| `AGENT_SUPERVISOR_NO_AUTO_UPDATE` | не задана | `1` выключает фоновые обновления, остаются только уведомления |

Остальные переменные, семь состояний воркера и каталоги кэша, которые песочница открывает по умолчанию, — в [справочнике](docs/reference.en.md).

Обновления происходят сами. При старте сервер в фоне спрашивает реестр npm и, если есть версия новее, отдельный процесс запускает `npm i -g`. Текущая сессия не затрагивается, следующая стартует уже на новой версии. Это работает только для глобальной установки.

Удаление:

```bash
npm uninstall -g agent-supervisor-mcp
claude mcp remove -s user agent-supervisor
codex mcp remove agent-supervisor
rm -rf ~/.claude/skills/agent-supervisor ~/.agents/skills/agent-supervisor ~/.codex/skills/agent-supervisor ~/.agent-supervisor
```

## Если что-то не так

| Симптом | Причина | Что сделать |
|---|---|---|
| Нет в `claude mcp list` | Установка не запустила `postinstall` | `agent-supervisor-setup` |
| Воркер сразу `failed`, `spawn codex ENOENT` | В `PATH` процесса нет codex | Задайте `CODEX_BIN` |
| `codex only resolved to a shell shim` | Windows нашла только `.cmd`, точки входа пакета нет | Переустановите `@openai/codex` или направьте `CODEX_BIN` на `codex.js` |
| `Cannot find module 'node:sqlite'` | Node старше 22.13.0 | Обновите Node |
| Воркер в состоянии `lost` | Воркер или его процесс запуска убили | Прочитайте события, затем `resume_worker` |
| Воркер в состоянии `timed_out` | Кончился бюджет времени, и его остановили | Посмотрите, что он оставил; после лимита на один запуск — `resume_worker`, после общего лимита — `followup_of` с новыми `limits` |
| `git add` падает с `index.lock: Operation not permitted` | Песочница делает `.git` доступным только для чтения. Так и задумано | Пусть коммитит `land_worker` с `commit_message` |
| `owned_paths overlap with active worker(s)` | Два воркера заняли одни и те же пути | Разделите работу иначе или отмените того, кто их держит |
| Доска пустая | У доски и MCP-сервера разные `SUPERVISOR_HOME` | Направьте оба в один каталог |
| `port 7877 ... is already in use` | Доска уже запущена | Откройте её или поменяйте `SUPERVISOR_WEB_PORT` |

## Известные ограничения

- Worktree нарезается из коммита. Незакоммиченных изменений из вашей рабочей копии в нём нет.
- Изолирован только рабочий каталог. Временные каталоги, базы данных и порты общие.
- Защита блокирует прямую запись файлов, но это не файловая песочница. Разрешённый вами скрипт может что-то сделать за пределами объявленных путей; это ловит проверка diff перед вливанием.
- Приёмка проверяет то, что вы написали в `acceptance`, и больше ничего. Остальное — это основной поток, читающий diff.
- Таймаут MCP-инструмента у клиента — жёсткая стена, поэтому один вызов `wait_workers` не может ждать до конца. Вызовите его снова.
- `find_works` ищет по подстроке, этого хватает на несколько сотен задач. Векторный поиск не планируется.

## Разработка

```bash
npm install
npm test               # прогон на fake-codex, меньше минуты
npm run test:real      # настоящий codex CLI от начала до конца; нужен залогиненный codex
npm run web:dev        # разработка доски, /api проксируется на 7877
```

CI работает на Ubuntu, macOS и Windows, плюс отдельная задача на Node 22.13.0, которая фиксирует нижнюю границу `engines`.
